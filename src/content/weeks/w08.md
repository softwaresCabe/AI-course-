## 8.1 Decoding: turning probabilities into text

At each step the model outputs logits over the vocabulary; a **decoding strategy** picks the next token.

- **Greedy**: take the argmax. Deterministic, can loop or be bland.
- **Temperature** T: sample from `softmax(z / T)`. T < 1 sharpens (more deterministic), T > 1 flattens (more diverse). T → 0 approaches greedy.
- **Top-k**: sample only among the k most likely tokens.
- **Top-p (nucleus)**: sample from the smallest set whose cumulative probability ≥ p (e.g. 0.9). Adapts to the model's confidence.
- **Min-p**: keep tokens with probability ≥ p_min × p(top token).
- **Beam search**: track several high-probability partial sequences; good for translation, rarely used for chat.
- **Constrained / structured decoding**: mask tokens that would violate a grammar or JSON schema, guaranteeing valid structure (Week 9).

Note: temperature 0 is not always perfectly deterministic in production because of batching and floating-point non-associativity on GPUs.

## 8.2 Prefill vs decode and the KV cache

Generation has two phases:
1. **Prefill**: process the whole prompt in parallel. **Compute-bound** (big matmuls). Sets **time to first token (TTFT)**.
2. **Decode**: generate one token at a time. Each step needs the keys and values of *all* previous tokens. **Memory-bandwidth-bound**: every step must read all the model weights (and the cache) from GPU memory to do relatively little math.

The **KV cache** stores K and V for every past token in every layer so they aren't recomputed:

```
KV bytes per token = 2 (K and V) × n_layers × n_kv_heads × d_head × bytes_per_value
```

Example: 32 layers, 8 KV heads (GQA), d_head = 128, fp16 (2 bytes) → `2·32·8·128·2 = 131,072 bytes ≈ 128 KB per token`. A 32k-token context → ~4 GB per sequence. Without GQA (32 KV heads) it would be 4× larger. The KV cache, not the weights, often limits how many concurrent users a GPU can serve.

## 8.3 Why decode is memory-bound: a roofline view

A GPU has peak compute (FLOP/s) and peak memory bandwidth (bytes/s). **Arithmetic intensity** = FLOPs per byte moved. Decoding a single sequence does ~2 FLOPs per parameter while reading ~2 bytes per parameter (fp16) → intensity ≈ 1, far below what GPUs need to be compute-bound (hundreds). So:

```
max tokens/s for one sequence ≈ memory bandwidth / model size in bytes
```

A 70B model in fp16 (140 GB) with ~3.35 TB/s of memory bandwidth (one H100’s HBM): ≈ 24 tokens/s upper bound per sequence. In practice the model is too big for one 80 GB GPU, so it is sharded across GPUs with tensor parallelism, which raises the aggregate bandwidth and the bound. **Batching** many sequences reuses each weight read for many tokens, raising throughput almost for free until compute becomes the bottleneck.

## 8.4 Serving systems

- **Continuous (in-flight) batching**: add and remove sequences from the running batch at every step instead of waiting for the whole batch to finish. Huge throughput gains (Orca, vLLM, TGI, TensorRT-LLM, SGLang).
- **PagedAttention** (vLLM): manage the KV cache in fixed-size blocks like OS virtual-memory pages, eliminating fragmentation and enabling sharing.
- **Prefix caching**: reuse KV for repeated prompt prefixes (system prompts, documents). Provider APIs expose this as **prompt caching** with large discounts on cached input tokens — design prompts with stable content first and variable content last.
- **Disaggregated prefill/decode**: run the two phases on different GPU pools.
- **FlashAttention**: computes exact attention in tiles that fit in fast on-chip SRAM, never materializing the full n×n matrix in high-bandwidth memory — much faster and O(n) memory.

## 8.5 Making models smaller and faster

**Quantization** stores weights (and sometimes activations/KV) with fewer bits:
- **fp16/bf16** (2 bytes) → **int8/fp8** (1 byte) → **4-bit** (GPTQ, AWQ, GGUF formats for llama.cpp).
- Weight-only 4-bit roughly quarters memory vs fp16 and speeds up memory-bound decode, usually with modest quality loss; always evaluate on *your* tasks, especially reasoning and long context.
- **KV-cache quantization** extends effective context and concurrency.

Other techniques:
- **Speculative decoding**: a small **draft** model proposes several tokens; the big model verifies them in one parallel forward pass and accepts the longest correct prefix. Output distribution is *identical* to the big model; speedups of ~2–3× are common when the draft is good. Variants: Medusa heads, EAGLE, lookahead decoding.
- **Distillation** into smaller models (Week 7).
- **Pruning** and **MoE** (fewer active parameters per token).

## 8.6 The metrics that matter

- **TTFT** (time to first token) — perceived responsiveness; dominated by prefill and queueing.
- **TPOT / ITL** (time per output token / inter-token latency) — streaming smoothness.
- **Throughput** (tokens/s per GPU) — cost efficiency.
- **Goodput**: requests/s that meet latency SLOs.
- **Cost**: $ per million input/output tokens. Output tokens typically cost several times more than input tokens with API providers because decode is the expensive phase.

Trade-off: bigger batches raise throughput and lower cost but increase per-request latency. Your product decides where to sit (voice ordering needs low TTFT; nightly batch classification wants max throughput — use provider **batch APIs** for big discounts).

## 8.7 Running models yourself vs APIs

| Option | Pros | Cons |
|---|---|---|
| Frontier API | Best quality, zero ops, fast to ship | Per-token cost, data governance review, rate limits |
| Hosted open-weight (inference providers) | Cheaper, model choice | Quality gap on hard tasks, vendor variety |
| Self-host (vLLM/SGLang on GPUs) | Control, privacy, cost at high steady volume | GPU ops, utilization risk, on-call |
| On-device / edge (llama.cpp, MLX) | Offline, private, no per-call cost | Small models only |

For a POS or warehouse system that must work offline (as in a festival deployment), a small quantized local model for narrow tasks plus a cloud model when connected is a realistic hybrid.
