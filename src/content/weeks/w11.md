## 11.1 What is an agent?

An **agent** is an LLM running in a loop, choosing actions (tool calls) based on observations, until a goal is achieved:

```
while not done and steps < max_steps:
    action = model(goal, context, observations)     # think + choose a tool
    observation = execute(action)                  # your code runs it
    context = update(context, action, observation)
```

Anthropic's "Building effective agents" distinguishes **workflows** (LLMs and tools orchestrated through *predefined* code paths) from **agents** (the LLM *dynamically* directs its own process and tool use). Start with the simplest thing that works: a single well-prompted call, then a workflow, and only then an autonomous agent when the task is open-ended and the path can't be predicted.

## 11.2 Workflow patterns

- **Prompt chaining**: fixed sequence of steps with checks between them (outline → validate → draft).
- **Routing**: classify the input, send it to a specialized prompt/model/tool.
- **Parallelization**: run independent subtasks simultaneously (sectioning), or the same task several times and aggregate (voting).
- **Orchestrator–workers**: a lead model breaks a task into subtasks dynamically and delegates to workers, then synthesizes.
- **Evaluator–optimizer**: one model generates, another critiques against criteria, loop until it passes.

These cover most production needs with far more predictability than a free-roaming agent.

## 11.3 The agent loop in depth

Key design elements:
- **Reasoning + acting interleaved** (ReAct, Yao et al., 2022): the model reasons about what to do, acts, observes, and reasons again. Modern models do this natively with tool use and interleaved thinking.
- **Planning**: explicit plans (todo lists) help on long tasks; let the agent revise the plan as it learns.
- **Stopping criteria**: goal reached, step/time/cost budget exhausted, or a human checkpoint.
- **Ground truth from the environment**: agents work best where each step produces verifiable feedback — tests passing, a query returning rows, a page rendering. This is why **coding agents** are the most mature agent category.
- **Error recovery**: surface tool errors as observations; detect loops (same action repeated) and change strategy or escalate.

## 11.4 Memory and long-horizon work

Context windows are finite and costly; long tasks need memory management:
- **Short-term**: the running context; **compaction** summarizes older turns and drops raw tool outputs once used.
- **Long-term**: external stores — files, databases, vector stores — the agent reads/writes via tools (e.g. a NOTES.md or progress file).
- **Structured state**: todo lists, plans and progress logs let an agent (or a fresh agent) resume work.
- **Sub-agents**: delegate a focused subtask to a separate agent with a clean context; it returns a condensed result, keeping the main context lean.

## 11.5 Model Context Protocol (MCP)

**MCP** (introduced by Anthropic in late 2024, now widely adopted across the industry) is an open protocol that standardizes how AI applications connect to tools and data — often described as a "USB-C port for AI".

- **Hosts/clients** (e.g. Claude apps, IDEs, your own agent) connect to **MCP servers**.
- Servers expose **tools** (actions), **resources** (readable data), and **prompts** (reusable templates).
- Transports: **stdio** for local servers, **Streamable HTTP** for remote servers, with OAuth-based authorization for remote access.
- Benefit: write an integration once (say, an inventory server for a warehouse system) and any MCP-compatible agent can use it.

```ts
import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import { z } from "zod"; // zod v4

const server = new McpServer({ name: "acme-inventory", version: "1.0.0" });
server.registerTool(
  "check_stock",
  {
    description: "Return on-hand quantity and bin location for a SKU in a given warehouse.",
    inputSchema: z.object({ sku: z.string(), warehouseId: z.string() }),
  },
  async ({ sku, warehouseId }) => {
    const row = await db.stock.find(sku, warehouseId);   // your data layer
    return { content: [{ type: "text", text: JSON.stringify(row) }] };
  },
);
await server.connect(new StdioServerTransport());
```

(This is the v2 SDK, published as `@modelcontextprotocol/server`. The older v1.x line used the `@modelcontextprotocol/sdk` package and a variadic `server.tool(name, description, shape, handler)` helper, which v2 removed in favor of `registerTool`. Check the current SDK docs, since the API keeps evolving.)

## 11.6 Multi-agent systems

Multiple agents can parallelize breadth-first work (e.g. a lead researcher spawning sub-agents to explore different sources). Benefits: parallelism, separation of concerns, cleaner contexts. Costs: many more tokens (Anthropic reported its multi-agent research system used about 15× the tokens of a chat interaction, versus about 4× for a single agent), coordination failures, duplicated work, and harder debugging. Use them when the task is valuable and genuinely parallelizable — not by default.

## 11.7 Failure modes and safety

- **Compounding errors**: a 95%-reliable step repeated 20 times succeeds end-to-end only ~36% of the time (0.95²⁰). Shorten chains, add verification, checkpoints and retries.
- **Looping and runaway cost**: enforce budgets on steps, tokens, time and money.
- **Prompt injection via tool results**: a web page or email can instruct the agent to exfiltrate data. Treat all tool output as untrusted (Week 12).
- **Excessive agency**: limit permissions; sandbox code execution (containers, no network by default); require human approval for irreversible or external actions (payments, emails, deletes, deploys).
- **Observability**: log every step — prompts, tool calls, arguments, results, costs — with trace IDs, so you can replay and debug.

## 11.8 Evaluating agents

- **Task success rate** on realistic tasks with verifiable end states (tests pass, DB in correct state).
- **Efficiency**: steps, tokens, wall-clock, cost per success.
- **Trajectory quality**: unnecessary tool calls, unsafe actions attempted, recovery from errors.
- **pass@k vs pass^k**: pass@k = at least one of k attempts succeeds (capability); pass^k = all k succeed (reliability — what production needs).
- Public benchmarks: SWE-bench (code), τ-bench (tool use with simulated users), WebArena/OSWorld (web/computer use), GAIA. Your own task suite matters most.
