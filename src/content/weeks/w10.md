## 10.1 Why retrieval?

LLMs know what was in their training data, up to a cutoff, imperfectly. They don't know your company's documents, today's inventory, or a customer's order history. **Retrieval-Augmented Generation (RAG)** (Lewis et al., 2020) fetches relevant information at query time and places it in the context so the model can answer **grounded** in sources — with citations, fresh data, access control and far less hallucination than relying on parametric memory.

The pipeline:

```
INDEXING (offline):  documents → parse → chunk → embed → store (vector + metadata + text)
QUERY (online):      question → (rewrite) → retrieve top-k → rerank → build prompt → generate → cite
```

## 10.2 Embeddings for retrieval

An **embedding model** maps text to a dense vector such that semantically similar texts are close (cosine similarity). Retrieval embedders are usually trained **contrastively**: pull (query, relevant passage) pairs together and push apart random/hard negatives (InfoNCE loss).

Choosing a model: check retrieval benchmarks (e.g. MTEB) *and* test on your own data; consider dimension (storage/speed), max input length, multilingual support, and cost. Some models support **Matryoshka** embeddings — truncate to fewer dimensions with graceful quality loss.

Rules:
- Use the **same model** for documents and queries (some models need distinct query/document prefixes).
- Changing the embedding model means **re-embedding everything** — version your indexes.

## 10.3 Chunking

Documents are split into chunks so retrieval returns focused passages.
- **Fixed-size** (e.g. 300–800 tokens) with **overlap** (10–20%) — a simple, strong baseline.
- **Structure-aware**: split on headings, paragraphs, code functions, table rows; keep the title/section path in each chunk.
- **Contextual chunking**: prepend a short, LLM-generated summary situating the chunk within its document before embedding ("This chunk is from the 2025 returns policy, section on perishables…"). Anthropic's *Contextual Retrieval* reported large reductions in retrieval failures by combining contextual embeddings and contextual BM25, with further gains from reranking.
- Too small → lost context; too large → diluted embeddings and wasted tokens. Tune on an eval set.

Store **metadata** with every chunk: source, URL, section, date, tenant ID, permissions. Metadata enables **filtering** ("only this restaurant's documents", "only docs updated after March") — mandatory for multi-tenant SaaS.

## 10.4 Vector search

Exact nearest-neighbor search compares the query with every vector — O(N). **Approximate nearest neighbor (ANN)** indexes trade a little recall for big speedups:
- **HNSW** (Hierarchical Navigable Small World): a multi-layer proximity graph; greedy search from coarse to fine layers. Excellent recall/latency; memory-heavy. Default in many systems.
- **IVF** (inverted file): cluster vectors with k-means, search only the nearest clusters (`nprobe`). Often combined with **product quantization (PQ)** for compression.

Where to store vectors:
- **pgvector** in Postgres — ideal when your app already runs Postgres: vectors live next to relational data, you get transactions, joins, and row-level security for tenant isolation. Supports HNSW and IVFFlat indexes.
- Dedicated vector databases (Pinecone, Weaviate, Qdrant, Milvus, etc.) — for very large scale or specialized features.
- Search engines with vector support (Elasticsearch/OpenSearch).

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id bigserial PRIMARY KEY, tenant_id uuid NOT NULL, doc_id uuid,
  content text NOT NULL, embedding vector(1024)
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
-- top-5 for one tenant (<=> is cosine distance)
SELECT id, content FROM chunks
WHERE tenant_id = $1
ORDER BY embedding <=> $2
LIMIT 5;
```

Gotcha: an approximate index plus a selective filter can silently return **fewer than k rows**. HNSW finds the nearest `ef_search` candidates first (default 40) and the `WHERE tenant_id = …` filter is applied afterwards, so a small tenant may get 0–2 results. Fixes: enable **iterative index scans** (pgvector 0.8+: `SET hnsw.iterative_scan = relaxed_order;`), raise `hnsw.ef_search`, use **partial indexes** or partitions per large tenant, or fall back to exact search for small tenants. Test retrieval for your smallest tenant, not just your largest.

## 10.5 Hybrid search and reranking

Dense embeddings capture meaning but can miss exact tokens: SKUs, error codes, names, part numbers. **Lexical search** (**BM25**: term-frequency × inverse-document-frequency with length normalization) nails exact matches. **Hybrid search** runs both and fuses rankings, commonly with **Reciprocal Rank Fusion**:

```
RRF(d) = Σ_over_rankers  1 / (k + rank_r(d)),   k ≈ 60
```

**Reranking**: retrieve a generous candidate set (e.g. top 50–100) cheaply, then rescore with a **cross-encoder** that reads the query and passage *together* (more accurate than comparing two independent embeddings, but too slow to run over the whole corpus). Keep the top 5–20 for the prompt.

**Bi-encoder vs cross-encoder**: bi-encoders embed query and doc separately (precomputable, fast); cross-encoders attend across both (accurate, expensive).

## 10.6 Query-side techniques

- **Query rewriting**: turn a chatty follow-up ("what about the other one?") into a standalone query using conversation history.
- **Multi-query / decomposition**: generate several sub-queries and union results.
- **HyDE**: generate a hypothetical answer and embed it to search.
- **Routing**: decide which index/tool (docs, SQL database, web) suits the question. For structured questions ("total sales last week"), **text-to-SQL** with a read-only role beats vector search.
- **Agentic RAG**: let an agent iteratively search, read and refine (Week 11).

## 10.7 Generation and grounding

Prompt the model to answer **only from the provided sources**, cite them (e.g. `[doc-3]`), and say "I don't know" when the sources don't contain the answer. Put sources in clearly delimited blocks with IDs. Post-process to verify that cited IDs exist. Treat retrieved text as **untrusted** — documents can contain prompt injections (Week 12).

Long-context models don't eliminate RAG: retrieval still wins on cost, latency, freshness, permissions and scale (millions of documents), though for a handful of documents, stuffing them into context can be simpler.

## 10.8 Evaluating RAG

Evaluate **retrieval** and **generation** separately:
- Retrieval: **Recall@k** (is a relevant chunk in the top k?), **MRR** (mean reciprocal rank of the first relevant hit), **nDCG**.
- Generation: **faithfulness/groundedness** (claims supported by retrieved context), **answer relevance/correctness**, **citation accuracy**.
- Build a **golden set** of real questions with known relevant sources and reference answers (start with 50–200). Use LLM-as-judge carefully, calibrated against human labels (Week 12).
- Track failures by stage: parsing → chunking → retrieval → reranking → generation. Most RAG bugs are retrieval bugs.

## 10.9 Week summary

You can build a production RAG pipeline end to end: parsing, chunking with metadata, embedding, ANN indexing with pgvector, hybrid BM25 + dense retrieval with RRF, cross-encoder reranking, grounded generation with citations, multi-tenant filtering, and stage-wise evaluation.
