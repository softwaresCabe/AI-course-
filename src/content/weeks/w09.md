## 9.1 The AI engineer's job

Phase III shifts from *how models work* to *how to build reliable products with them*. An AI engineer designs systems around a probabilistic component: they specify behavior with prompts and context, connect models to tools and data, measure quality with evals, and operate the whole thing in production. The defining skill is turning "it worked in the playground" into "it works 99% of the time for real users, at a known cost".

## 9.2 Anatomy of an LLM API call

Every major provider API has the same shape:

```ts
const res = await client.messages.create({
  model: MODEL_ID,
  system: "You are Acme Logistics' warehouse assistant. ...",   // role, rules, context
  messages: [
    { role: "user", content: "Which orders are at risk of missing today's carrier cutoff?" },
  ],
  tools: [/* JSON-schema tool definitions */],
  max_tokens: 4096,
});
```

Concepts: **system prompt** (persistent instructions), **message history** (the model is stateless — you resend the conversation every call), **context window** (max tokens of input + output), **stop reasons** (end of turn, max tokens, tool use, refusal — check it before reading the content), **streaming** (server-sent events for low perceived latency), and **usage** (input/output/cached tokens → cost).

Sampling knobs are provider- and model-specific. Older APIs exposed `temperature`/`top_p` on every call; several current frontier models (including recent Claude models) reject them and instead expose a reasoning **effort** setting. Steer determinism and style through the prompt, examples and structured output rather than relying on temperature, and check the current docs for the model you deploy.

## 9.3 Prompt engineering that actually works

Treat prompts as **code**: version-controlled, reviewed, tested against an eval set.

1. **Be explicit and specific**. State the task, audience, constraints, and what "done" looks like. Explain *why* rules exist — models generalize better from reasons than from bare commands.
2. **Give context**. The model knows nothing about your business; include the relevant data, definitions and edge cases.
3. **Use structure**. Separate instructions from data with clear delimiters (e.g. XML-style tags like `<order>` … `</order>` or markdown sections). This also reduces prompt-injection confusion.
4. **Show examples (few-shot)**. 2–5 diverse, representative examples, including tricky edge cases. Beware: models copy surface features of examples too.
5. **Let it think**. For complex tasks, use a reasoning model and raise its thinking **effort** (current APIs let the model decide how much to think — e.g. adaptive thinking — rather than taking a fixed token budget), or ask for reasoning before the answer. Don't force step-by-step on simple lookups — use low effort there; extra thinking adds cost and latency.
6. **Specify the output format** precisely, ideally with a schema.
7. **Assign a role** when it helps set expertise and tone.
8. **Decompose** big tasks into a chain of smaller prompts (extract → validate → transform → summarize), each testable.

Anti-patterns: vague goals ("make it better"), contradictory rules, giant unstructured walls of text, relying on ALL-CAPS threats, and never measuring.

## 9.4 Structured outputs

Production systems need machine-readable output. In increasing order of reliability:
1. Ask for JSON in the prompt and parse defensively.
2. Provide a **JSON Schema** and use the provider's **structured output / JSON mode**, or define a tool whose input schema is your desired output.
3. **Constrained decoding** (self-hosted: Outlines, XGrammar, llama.cpp grammars) — invalid tokens are masked so output is guaranteed to parse.

Always **validate** with a schema library (Zod in TypeScript, Pydantic in Python), and on failure retry with the validation error fed back. Remember: valid JSON is not the same as *correct* content — still evaluate the values.

```ts
import { z } from "zod";
const Order = z.object({
  items: z.array(z.object({ sku: z.string(), qty: z.number().int().positive() })),
  pickup: z.enum(["asap", "scheduled"]),
  notes: z.string().optional(),
});
type Order = z.infer<typeof Order>;
```

## 9.5 Tool use (function calling)

Tool use lets a model *act*: query a database, call an API, run code. The loop:

1. You send tool definitions: `name`, `description`, `input_schema` (JSON Schema).
2. The model responds with a **tool-use request** (tool name + arguments) instead of, or alongside, text.
3. **Your code executes the tool** — the model never runs anything itself — and returns a **tool result** message.
4. The model continues, possibly calling more tools, until it produces a final answer.

Tool design is product design:
- **Clear names and rich descriptions** (when to use it, what it returns, units, limits). The description is a prompt.
- **Few, well-scoped tools** beat dozens of overlapping ones.
- **Return concise, model-friendly results** — not 50 KB of raw JSON. Paginate and summarize.
- **Errors as information**: return actionable error messages ("SKU not found; did you mean ...") so the model can recover.
- **Least privilege**: read-only by default; require confirmation for consequential actions (refunds, emails, deletes).
- Validate arguments server-side — never trust model-generated parameters, especially for SQL or shell.

## 9.6 Context engineering

Model quality is bounded by what's in the context window. **Context engineering** is deciding what goes in, in what order, and what gets left out:

- **Relevance over volume**: long contexts dilute attention, increase cost and latency; models can miss facts buried in the middle ("lost in the middle"), though modern models are much better at long-context retrieval than early ones.
- **Ordering**: put long documents first and the question/instructions at the end for long-context tasks; keep stable content first for prompt caching.
- **Memory and summarization**: for long conversations or agent runs, compact older turns into summaries, store durable facts externally, and retrieve them when relevant.
- **Just-in-time retrieval**: give the model tools to fetch information when needed instead of stuffing everything upfront.
- **Token budgeting**: reserve room for output and tool results; measure token counts in tests.

## 9.7 Reliability patterns

- **Retries with backoff** for rate limits (429) and transient errors; set **timeouts**.
- **Fallback models** and graceful degradation (e.g., fall back to a rules engine when the LLM is down — essential for POS systems).
- **Caching** responses for identical deterministic requests.
- **Guardrails**: input/output classifiers, schema validation, business-rule checks before acting.
- **Human-in-the-loop** for low-confidence or high-impact outputs.
- **Model routing**: send easy requests to a small fast model and hard ones to a frontier/reasoning model.

## 9.8 Week summary

You can call LLM APIs with streaming and tools, write structured prompts with examples and clear output formats, enforce and validate structured output with Zod/Pydantic, design good tools, engineer context for quality and cost, and wrap LLM calls with production reliability patterns.
