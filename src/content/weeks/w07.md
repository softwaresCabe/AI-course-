## 7.1 From base model to assistant

Post-training turns a document-completer into a helpful, honest, harmless assistant — and, increasingly, into a strong **reasoner** and **agent**. The usual pipeline:

1. **Supervised fine-tuning (SFT)** on high-quality demonstrations (prompt → ideal response), formatted with a **chat template** (system/user/assistant roles marked with special tokens).
2. **Preference optimization** — RLHF, DPO, or AI-feedback variants — to push toward responses people (or a constitution) prefer.
3. **Reinforcement learning with verifiable rewards** for math, code and agentic tasks, which produces long chains of reasoning.
4. **Safety training and evaluation** throughout.

Post-training uses orders of magnitude less compute than pretraining but has outsized effects on usefulness. The pretrained model has the knowledge; post-training shapes *how* it is used.

## 7.2 Supervised fine-tuning

SFT is ordinary next-token training, but the loss is usually computed **only on assistant tokens** (prompt tokens are masked) so the model learns to *respond*, not to imitate users. Key lessons:
- **Quality ≫ quantity**: thousands of excellent, diverse examples can beat millions of mediocre ones (e.g. the LIMA paper).
- The chat template must match exactly between training and inference.
- SFT teaches format and style quickly but can encourage confident **hallucination** if demonstrations contain facts the model doesn't actually know.

## 7.3 RLHF: reward models + policy optimization

**InstructGPT** (Ouyang et al., 2022) popularized the recipe:
1. Collect **comparisons**: for a prompt, humans rank two or more model responses.
2. Train a **reward model (RM)** `r(x, y)` with the Bradley–Terry loss: `−log σ(r(x, y_win) − r(x, y_lose))`.
3. Optimize the policy with RL (classically **PPO**) to maximize `E[r(x, y)] − β · KL(π_θ ‖ π_ref)`.

The **KL penalty** keeps the policy near the SFT reference model, preventing it from drifting into weird text that happens to fool the reward model — **reward hacking** (Goodhart's law: "when a measure becomes a target, it ceases to be a good measure"). Classic RLHF failure modes: verbosity bias, **sycophancy** (agreeing with the user), over-refusal.

## 7.4 Direct Preference Optimization (DPO) and friends

**DPO** (Rafailov et al., 2023) shows the KL-regularized RLHF objective has a closed-form optimal policy, which lets you skip the explicit reward model and RL loop. You train directly on preference pairs:

```
L_DPO = −log σ( β · [ log π(y_w|x)/π_ref(y_w|x) − log π(y_l|x)/π_ref(y_l|x) ] )
```

It's stable, simple (like supervised training), and widely used for open models. Variants include IPO, KTO (works from thumbs-up/down rather than pairs) and ORPO. Trade-off: purely offline methods can't explore beyond the collected responses; online RL can.

## 7.5 AI feedback and Constitutional AI

Human labels are expensive and inconsistent. **Constitutional AI** (Anthropic, Bai et al., 2022) uses a written set of principles: the model critiques and revises its own outputs (supervised phase), then an AI model judges which of two responses better follows the constitution, producing preference data for RL (**RLAIF**). Benefits: scalability, transparency of the principles, and the ability to train harmlessness without humans reading large volumes of harmful content.

## 7.6 Reasoning models and RL with verifiable rewards

Since 2024, a major capability jump came from training models to **think before answering**. Recipe (e.g. OpenAI's o1 line, DeepSeek-R1 and others): run RL on problems with **automatically checkable answers** — math with known solutions, code with unit tests, puzzles — rewarding correct final answers (**RLVR**). Models learn to produce long **chains of thought**: decomposing problems, checking work, backtracking.

- **GRPO** (Group Relative Policy Optimization, from DeepSeekMath) samples a group of responses per prompt and uses each response's reward *relative to the group mean* as its advantage — no separate value network needed.
- This creates **test-time compute scaling**: more thinking tokens → better accuracy on hard problems, a new lever alongside model size.
- Risks: reward hacking against weak verifiers (e.g. special-casing unit tests), unfaithful or illegible reasoning, and higher latency/cost.

**Distillation**: a large reasoning model's traces can be used to SFT a smaller model, transferring much of the capability cheaply.

## 7.7 Parameter-efficient fine-tuning: LoRA and QLoRA

Full fine-tuning updates all weights (~16 bytes/param of state). **LoRA** (Hu et al., 2021) freezes the base weights and learns a low-rank update for selected matrices:

```
W' = W + (α / r) · B A        A: (r × d_in), B: (d_out × r), r ≈ 8–64
```

B is initialized to zero, so training starts exactly at the base model. Benefits: ~0.1–1% trainable parameters, tiny checkpoints (MBs), multiple adapters can be swapped on one base model at serving time.

**QLoRA** (Dettmers et al., 2023) loads the frozen base in **4-bit NF4** quantization and trains LoRA adapters in higher precision, enabling fine-tuning of a ~65B model on a single 48GB GPU.

## 7.8 When should *you* fine-tune?

A decision ladder for production:
1. **Prompting / context engineering** first (Week 9). Cheapest, fastest to iterate.
2. **RAG** when the model lacks *knowledge* (your docs, current data) — Week 10.
3. **Fine-tuning** when you need consistent *behavior*: a format, style, domain jargon, tool-calling patterns, or to make a small model match a big one on a narrow task (lower cost/latency).
4. **Preference tuning / RL** when you have a clear reward signal or comparison data.

Fine-tuning is **bad** at reliably injecting lots of new facts and can cause **catastrophic forgetting** or degrade safety behaviors. Always evaluate against a held-out set and the base model.
